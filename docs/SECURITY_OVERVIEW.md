# Security overview

PlantGuard AI remains a simulation-only demonstration. The authentication boundary protects simulated mutations; it does not authorize or control physical equipment.

## Authentication architecture

1. The operator submits the configured username and password to the same-origin Next.js authentication route. Production use requires HTTPS.
2. The Next.js server verifies the password against a configured scrypt password hash and applies Redis-backed login attempt limits.
3. Before granting a session, Next.js confirms that the backend's token-protected `/api/v1/auth/status` accepts the server-configured mutation token.
4. Next.js creates a random opaque session ID and CSRF nonce. Redis stores their session record with a 30-minute TTL; Redis stores only a hash of the session ID as the key.
5. The session ID is set in an `HttpOnly`, `SameSite=Strict` cookie. Production requires HTTPS and the `Secure`, `__Host-` cookie policy. Local development explicitly requires an HTTP loopback origin and `PLANTGUARD_COOKIE_SECURE=false`.
6. State-changing proxy requests require the server-side session, a matching in-memory CSRF header, and the exact configured origin. The proxy forwards the backend mutation token only from its server environment.
7. Logout deletes the Redis session and clears the cookie. Redis expiry invalidates abandoned sessions; if Redis is unavailable, authentication and mutations fail closed.

The browser handles the operator's ordinary login password transiently, as in a conventional web login. It never receives the backend mutation token. Passwords are not stored in browser storage, HTML, URLs, or responses. A short-lived CSRF nonce may be held in client memory; it is not an authentication credential.

## Configuration

The frontend server requires:

- `PLANTGUARD_OPERATOR_USERNAME`
- `PLANTGUARD_OPERATOR_PASSWORD_HASH` (generated by `node scripts/generate_operator_password_hash.mjs`; keep it in a secret manager, not source control)
- `PLANTGUARD_SESSION_STORE_URL` (`redis://` locally; use authenticated TLS Redis / `rediss://` for production)
- `PLANTGUARD_AUTH_ENV=development` or `production` (explicit policy selector)
- `PLANTGUARD_PUBLIC_ORIGIN` (exact origin, including scheme and port)
- `PLANTGUARD_COOKIE_SECURE=false` only for local HTTP loopback; production requires `true` and an HTTPS public origin
- `PLANTGUARD_MUTATION_TOKEN` (server-only backend shared secret, at least 32 characters)
- `PLANTGUARD_API_URL` (server-only backend URL)

For production, set `PLANTGUARD_AUTH_ENV=production`, use an HTTPS `PLANTGUARD_PUBLIC_ORIGIN`, and set `PLANTGUARD_COOKIE_SECURE=true`. The application rejects auth changes unless it receives HTTPS directly or a trusted proxy's `X-Forwarded-Proto: https`. Set `PLANTGUARD_TRUST_PROXY=true` only when the trusted proxy strips client-supplied forwarding headers and supplies its own `X-Forwarded-For` and `X-Forwarded-Proto`; otherwise login limiting uses one conservative server bucket. Configure `PLANTGUARD_CORS_ORIGINS` as a strict backend allowlist; the Next.js server-to-server proxy does not require browser CORS credentials.

The Compose demo keeps Redis on its private Compose network with no published host port and no persistence; a Redis restart logs out active sessions. Production must use a managed or separately operated Redis service with TLS, authentication/ACLs, access restrictions, backups as appropriate, and monitoring. Do not copy production credentials into Compose files or image layers.

## Threat model and trust boundaries

- **Browser to Next.js:** untrusted input. Origin, content type, size, session, CSRF, and login attempt limits are checked server-side. XSS can still act as the current operator in that browser; use CSP and standard application hardening.
- **Next.js to Redis:** trusted server-to-server channel. Redis holds revocable sessions and short-lived rate-limit counters. Redis network access and credentials must be protected; compromise can disrupt/revoke sessions.
- **Next.js to backend:** trusted server-to-server channel. The mutation token is read from server environment and sent only in the Authorization header. Restrict backend network reachability and retain backend-side authentication.
- **Reverse proxy / TLS termination:** production must terminate TLS, enforce the exact public origin, strip incoming forwarding headers, and set trusted forwarding headers. Never set `PLANTGUARD_TRUST_PROXY=true` behind an untrusted proxy.
- **Operator account:** this version has one configured operator identity; it has no account lifecycle, MFA, per-user roles, SSO, or durable human audit trail.

## Implemented safeguards

- Backend simulator/advisory mutations require `PLANTGUARD_MUTATION_TOKEN`; strict request validation and backend CORS allowlisting remain active.
- The frontend proxy exposes only enumerated read and mutation routes.
- Server-side Redis sessions are random, opaque, revocable, and expire after 30 minutes.
- Login uses a scrypt password verifier, generic credential errors, and Redis-backed limits (five attempts per IP and username bucket in a 15-minute window).
- Mutations and logout require a valid session, same-origin request, and CSRF token. Login also requires the exact configured origin.
- Missing security configuration and unavailable Redis fail closed.
- Production cookie configuration requires HTTPS origin, `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/`, and the `__Host-` prefix. Local HTTP policy is explicitly limited to loopback.
- No shared backend secret is placed in browser storage, bundles, page HTML, URLs, or API response bodies.
- Recommendations and corrections remain advisory-only and modify only in-memory simulated state.

## Limitations

This is not a production release approval or a compliance certification. The configured single operator account is not a multi-user identity system. There is no MFA, credential rotation workflow, centralized audit trail, incident response, or protection against XSS/browser compromise. Production readiness still requires independent security review, secret-manager integration, Redis/TLS and reverse-proxy configuration verification, monitoring, and deployment-specific testing. Never connect this demo to plant/OT networks, PLCs, actuators, production data, or physical equipment.
